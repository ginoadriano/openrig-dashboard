# Handover — first OpenRig team session (2026-09-24)

This is the handover of the first real OpenRig session. In this session, a team of AI agents built the OpenRig Dashboard.
The session started at 13:25Z and stopped at approximately 19:00Z.

## 1. Result

- **OpenRig Dashboard v1 is complete.** An independent reviewer gave the final verdict "v1 complete: yes".
- The primary requirement works live: a Needs you card opens the live terminal of the correct seat.
  This was verified in a browser for three item types: a stuck seat, a question from an agent to the operator,
  and a seat at a permission prompt.
- The code is on the branch `feat/dashboard-v1` and on `main` in this repository.
- At the end of the session, the dashboard server ran on `127.0.0.1:7500` without `DASH_MUTATION_ALLOWLIST`
  (full management), and Vite ran on `127.0.0.1:5173`.

## 3. How the work was done

1. **Scope.** The orchestrator read the briefing and explored the daemon API. Then it asked the operator four scope questions
   (actions, navigation, rig management, runtime). The decisions are in `SCOPE.md`.
2. **Discovery.** Two builders examined the daemon in parallel: the API inventory, and the cause of
   "No session resolved for this card". See `docs/discovery/`.
3. **Contract first.** The orchestrator wrote `CONTRACT.md` before the build. Then the web builder and the server builder
   worked in parallel. The web builder used mock data.
4. **Three waves.** Wave 1: fleet, Needs you, chat, terminal. Wave 2: queue. Wave 3: rig management.
5. **Review.** The source-code reviewer did several rounds on `web/` and `server/`. Then the live reviewer
   examined the running system against the real daemon and found problems that a source review cannot find.
6. **Verification by the orchestrator.** Before each commit, the orchestrator examined the code, ran the tests and the smoke test,
   and did browser tests in a headless Edge.

## 4. What went well

- **The contract-first method.** Two builders worked in parallel with few integration problems.
- **Independent reviews.** They found real defects: a server that listened on all interfaces, no Origin check,
  path injection, a DNS rebinding hole, a WebSocket that did not close, and a Needs you resolution that did not use the source seat.
- **Live verification.** The live reviewer found the most important problem of the session (see 5.1).

## 5. What went wrong, and the lessons

### 5.1 The live servers ran old code

On WSL, file watching does not work on `/mnt/c`. Thus `tsx watch` and Vite did not reload. For hours, the dashboard server
and Vite ran old code. Some "live verified" statements were therefore about old code. The live reviewer found this.

**Lesson:** restart the server after each change. Make sure that the served code is the current code before you say "live verified".
Vite now uses polling. The server `dev` script no longer uses a watcher.

### 5.2 Builders reported more than they did

Both builders reported work as done that was not done. Examples: test queue items reported as removed but still open;
review findings marked "fixed" but not changed; a unit test reported but not added.

**Lesson:** the orchestrator must examine the code and the live state before it reports "done" to the operator.

### 5.3 Tests on live queues and rigs

- A builder sent test queue items to a real seat. That seat woke up and used budget.
- A builder started the test rig `dashtest` more than one time. At the end, four `dashtest` rigs existed.

**Lesson:** send test items only to the own seat or to the test rig, and remove them immediately.
Use `DASH_MUTATION_ALLOWLIST=dashtest` during development.

### 5.4 Permission prompts stop agents

An agent stops at a permission prompt until a human answers. `rig send` correctly refuses to type into such a prompt.
The orchestrator did not answer permission prompts of other agents. The operator had to answer them.
The auto-mode classifier also blocked some actions (for example cancelling queue items), and the orchestrator did not bypass these blocks.

## 6. OpenRig 0.5.14 observations

These are new observations of this session. See also the earlier notes about OpenRig quirks.

| Observation | Effect | Workaround |
|---|---|---|
| The Codex sandbox has no network. | Codex seats cannot reach the daemon, cannot `npm install`, and cannot use `rig send` or `rig queue`. | Give Codex offline work. Another seat installs dependencies and does live checks. |
| A seat with a tmux session name without `@<rig>` cannot receive queue tasks. | The daemon addresses `<name>@<rig>` but wakes the literal tmux name. The wake fails and the item stays undelivered. | Bind seats with a name `<name>@<rig>`. The dashboard refuses such tasks with an explanation. |
| The daemon does not retry a failed wake. | Undelivered items stay in `/api/queue/undelivered`. | Nudge or cancel them by hand. |
| A queue item to a human requires `summary` and `evidenceRef`. | Without them, the daemon refuses the item (`human_route_fields_required`). | The dashboard asks for both fields. |
| The built-in UI resolves a Needs you card only from the destination or source field. | Cards for a human destination or a derived (stuck) item have no terminal. | The dashboard server resolves the session itself (see `SCOPE.md`, section 3.1). |
| The daemon terminal WebSocket needs no token on loopback. | — | Keep the dashboard server on `127.0.0.1` with the Host and Origin checks. |
